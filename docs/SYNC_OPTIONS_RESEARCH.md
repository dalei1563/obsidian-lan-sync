# Obsidian 同步插件：三种后端方案可行性与实施方案

调研日期：2026-11-01。方案二按用户确认的定义：**完全使用 GitHub，正文、元数据和版本历史均在 GitHub 私有仓库中**。

后续进展：项目已选择自建路线并实现 v0.2 试用版，当前实现与验收情况见 [自建设计](LAN_SYNC_DESIGN.md) 和 [测试记录](LAN_SYNC_TEST_REPORT.md)。本文中的“项目现有基础”描述的是调研时状态。

本报告是架构调研与实施建议，没有执行新的远端写入、修改应用权限或启用真实 Vault 同步。下文分别标明项目已有实测、官方文档能力和工程设计；工作量属于估算。

## 1. 选型结论

三种方案都能实现桌面端 Markdown 双向同步，但适合的使用条件不同。

| 比较项 | 方案一：飞书云盘 + 多维表格 | 方案二：纯 GitHub | 方案三：局域网自建服务 |
|---|---|---|---|
| 总体判断 | 有条件可行，平台限制和鉴权需要先过关 | 可行，适合 Markdown 为主、可稳定访问 GitHub 的设备 | 可行，适合有常开设备且主要在内网同步 |
| 正文存储 | 云盘原格式不可变文件 | Git blob / 仓库中的 Markdown 文件 | 服务端本地不可变对象文件 |
| 元数据与历史 | 多维表格追加版本日志 | Git tree、commit + 必要的文件身份/冲突元数据 | SQLite 事务、版本记录、增量日志 |
| 一次发布正文与元数据 | 跨两个资源系统，需要应用层恢复 | 同一个 commit 可一起发布，以分支引用更新为可见边界 | 服务端统一控制；文件落盘与数据库提交仍须设计恢复顺序 |
| 并发处理 | 客户端维护版本图；同表写冲突重试 | 非强制分支更新 + 重新协调；插件仍须处理内容冲突 | 服务端事务维护版本图和唯一性 |
| 增量拉取 | 分页查询、重叠窗口、定期完整对账 | 检查分支 head，按固定 commit/tree 获取变化 | 单调递增序号 + 分页，推送只作提示 |
| 权限和账户 | 飞书应用权限、资源 ACL、正式鉴权组件 | 私有仓库权限、个人 token 或后续应用授权 | 用户/设备 token、Vault 隔离、内网 TLS |
| 延迟 | 首版建议分钟级轮询 | 首版建议分钟级轮询 | 可做秒级通知，需实测 |
| 外网跨设备 | 能访问飞书即可 | 能访问 GitHub 即可 | 默认仅内网；离开内网排队，回到内网同步 |
| 日常运维 | 不维护存储服务器；维护额度、权限与鉴权组件 | 不维护存储服务器；维护凭证、仓库和容量 | 维护常开主机、升级、磁盘与备份 |
| 扩展附件 | 可另做，但受接口与容量限制 | 少量小附件可评估，大量二进制历史不适合普通 Git | 最容易按需求扩展，但需自管容量和传输 |
| 项目现有基础 | 已有 SPEC、鉴权与资源配置原型 | 尚无后端实现 | 尚无服务端实现 |

**建议按使用条件选择：**

- 个人或小规模多设备、以 Markdown 为主、GitHub 连接稳定：优先方案二。一个后端即可同时承载内容与历史，不受多维表格版本日志行数约束。
- 已有 NAS/小主机、数据希望留在内网、主要在局域网同步：优先方案三。协议、并发和容量都由自己控制。
- 企业明确要求数据进入飞书、已有管理员支持和足够权益：方案一合理。它的主要价值是组织集成，而不是同步协议更简单。

不建议一开始同时实现三种后端。先选一种把可靠同步做完，再复用客户端引擎扩展其他后端。

## 2. 当前项目能复用什么

已检查 `README.md`、现有 SPEC、`src/main.ts`、`src/settings.ts`、`src/feishu/auth.ts` 及 `docs/` 中的验证记录。

| 项目 | 当前证据 | 对本次选型的含义 |
|---|---|---|
| 同步需求与安全约束 | 现有 SPEC 已定义不可变快照、版本 DAG、删除标记、冲突与恢复 | 大部分可作为三种方案的共同需求；原 SPEC 中“仅飞书”条款需选型后正式修订 |
| 插件代码 | 只有设置页、状态提示和鉴权探针 | 尚没有同步引擎，转换后端不会浪费大量已完成的同步代码 |
| 飞书鉴权 | 2026-10-29 记录获取应用令牌成功 | 证明当时测试环境能取令牌，不代表正式身份方案已完成 |
| 多维表格 | 已记录建表、索引增查清理、幂等重发和小规模并发分页探针 | 是方案一的有效基础，但不能推导出所有并发、超时、容量情形都通过 |
| 云盘文件传输 | 最后一次上传探针缺少相应 scope，原始字节往返未完成 | 方案一仍有明确 P0 阻断项 |
| 本地文件保护 | 只有 API 调查，没有 Windows/macOS 实机字节及竞争测试 | 三种方案都必须补齐，替换远端不能绕过这一问题 |

已有记录见 [API_VERIFICATION.md](API_VERIFICATION.md)、[OBSIDIAN_P0.md](OBSIDIAN_P0.md)、[TEST_REPORT.md](TEST_REPORT.md)。本次没有重跑这些实测，也没有把历史结果标为当前已验证。

沿用项目当前范围：Windows/macOS，原始 `.md` 文件，新建/修改/移动/删除，离线队列与冲突处理。附件、移动端、`.obsidian/` 配置同步分别评估，不自动纳入首版。

## 3. 三种方案共用的同步设计

后端能存文件只是起点，客户端必须知道“这次修改基于哪一个版本”。

```text
Vault 事件 + 启动/定期扫描
          ↓
文件身份与同步基线 → 本地持久化待提交队列
          ↓
协调引擎：比较基线、本地状态、远端版本
          ↓
后端适配器：Feishu / GitHub / LAN
          ↓
下载校验 → 本地写入保护 → 更新基线与游标
          ↘ 冲突中心 / 历史恢复
```

建议共同数据模型：

```text
vault_id, file_id, revision_id, parents[], operation,
path, content_hash, size, object_ref, client_id, schema_version
```

- `file_id` 表示逻辑文件，重命名不改变身份；路径不是身份。
- `revision_id` 是协议修订标识，不与飞书 token、Git commit SHA 混用。
- `parents[]` 记录真正基于的版本。两台设备基于同一旧版本修改，形成两个分支，保留双方。
- `content_hash` 对原始字节计算 SHA-256；时间戳只用于展示或辅助检索，不仲裁冲突。
- 删除是一条修订，即 tombstone。远端未列出某文件、接口 403、分页不完整都不能直接解释成删除。
- 上传前持久化操作及对应内容快照。仅记路径而不保存待提交内容，会在后续修改后失去重试同一操作的依据。
- 请求超时后先按修订标识对账；相同标识不同 payload 视为错误，不能覆盖。

本地应用远端结果时，使用逐文件队列、覆盖前重新校验、回声抑制和可恢复日志。必须区分“协议数据已经持久化”与“已经安全写入当前笔记”：游标只有在对应事件已应用，或已转存为持久化的待应用/冲突记录后才能推进。

Obsidian 官方文档说明 `Vault.process()` 可以保护同步回调中的读改写，并要求异步工作完成后在回调里重新比较内容；这不能扩展解释为任意二进制读写或外部进程竞争都已解决。现有要求同时涉及 BOM、CRLF 与编辑竞争，必须进行实机验证；若无法证明安全覆盖，就先保存远端冲突副本，暂停该文件自动替换。[Obsidian Vault 文档](https://docs.obsidian.md/Plugins/Vault)

其他共同规则：首次绑定预览双方差异；批量删除设置熔断；同名不同身份、路径大小写及 Unicode 冲突显式处理；下载内容校验哈希；路径拒绝越界；默认排除本插件状态和凭据。长时间离线设备再次接入时，保留删除历史，或要求基于新基线重新绑定，避免清理 tombstone 后旧文件复活。

## 4. 方案一：飞书云盘 + 飞书多维表格

### 4.1 可行性与关键限制

飞书官方提供原格式文件上传下载与多维表格记录接口，因此能力组合成立。应把 Markdown 当原始文件，不转换为飞书在线文档。[云文档能力与资源权限](https://open.feishu.cn/document/server-docs/docs/docs-overview?lang=zh-CN)

**多维表格可以存元数据，但不能按事务数据库使用。** 官方新增记录接口列出同表并发写冲突，说明底层写操作有串行限制。单个客户端将并发设为 1，只能约束自己，其他设备仍会同时写，必须支持退避与对账。接口的幂等参数也不能替代云盘与表格之间的跨系统事务。[新增记录接口](https://open.feishu.cn/document/server-docs/docs/bitable-v1/app-table-record/create)

**版本日志行数会持续增长。** 当前帮助中心列出基础/商业标准版起始 2,000 行，并有额外领取至 20,000 行的权益；其他版本和扩容权益不同。应检查实际表的权益及 API 行为，不能把 2,000、20,000 或 50,000 当作所有租户的统一上限。[多维表格行数与扩容](https://www.feishu.cn/hc/zh-CN/articles/389918352455-%E5%A4%9A%E7%BB%B4%E8%A1%A8%E6%A0%BC%E8%A1%8C%E6%95%B0%E6%89%A9%E5%AE%B9)

工程估算示例：初始 5,000 个文件，每天 300 条新修订，如果日志表可用容量为 20,000 行，剩余容量约能支持 `(20,000 - 5,000) / 300 = 50 天`。这是按假设计算，不是平台承诺。即使正文很小，追加日志也可能先耗尽。

**API 总量与接口频控是两回事。** 官方调用量公告存在明确标注为“2026 年 6 月限时”的 100 万次权益，不能用于承诺本报告日期的长期免费额度；应以租户管理后台当前权益为准。[自建应用 API 调用量公告](https://open.feishu.cn/document/uAjLw4CM/ukzMukzMukzM/platform-notices)

例如两台设备全天在线，每 10 分钟各查询一次，30 天仅空轮询就约有 `2 × 144 × 30 = 8,640` 次请求，尚未包含分页、上传、下载、日志和索引更新。需要将实际文件规模、在线时长、修订量代入预算，而不是只看每秒能调多少次。

**正式鉴权需要解决客户端 Secret。** 最新官方应用令牌文档要求 App Secret 留在服务端，不放客户端安装包。当前环境变量方式只保留为受控开发探针；正式版本建议使用受限 API 网关保存 Secret，并执行用户/Vault 授权，或先验证可用的用户授权流程。不能直接承诺“无需任何服务端且统一分发应用 Secret”。[飞书应用令牌与 Secret 要求](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/authentication-management/access-token/tenant_access_token)

### 4.2 建议架构

```text
Obsidian 插件 → 正式鉴权/受限 API 网关 → 飞书 OpenAPI
                                        ├─ 云盘 objects/：不可变正文
                                        └─ 多维表格
                                           ├─ revision_log：权威修订记录
                                           └─ file_index：可重建索引
```

延用现有 SPEC 的版本图模型。首版可以先省去 `current/` 可读镜像，减少请求与修复成本；若保留，它只能是缓存。飞书网页直接修改镜像，不会自动成为合法同步修订，必须另做“导入为新版本”流程。

上传顺序：

1. 本地持久化修订及正文快照。
2. 上传不可变正文，校验可读取与哈希；零字节正文采用经验证的协议表示。
3. 追加修订日志，包含对象 token、父修订、路径和哈希。
4. 对账确认日志可读后，才标记远端提交完成。
5. 异步更新索引/镜像；失败不撤销已提交修订。

正文成功、日志失败时，只留下待补交的孤立对象；日志成功但响应丢失时，按修订标识恢复。禁止先发布指向尚不存在正文的日志。

拉取使用分页和重叠查询窗口，按修订 ID 去重，并定期完整对账。不能将客户端时钟或“最后一个时间戳”当作无遗漏的数据库游标。达到一定规模后应增加可验证的快照与日志分段协议；仅按月份换表仍会无限增加新设备回放成本。

### 4.3 实施顺序与退出条件

1. **先补 P0**：专用目录上传下载、中文/BOM/CRLF/空文件、对象可读取、权限撤销、超时恢复、同表并发写入与分页完整性。
2. **核算权益**：实际云盘空间、目录文件数量限制、日志行数、API 月额度与端点频控；为目标规模做运行预算。网页上传额度不能替代 OpenAPI 上传限制。
3. **完成正式鉴权**：网关应限制目标资源与操作，避免仅把宽权限应用令牌发给所有客户端。
4. **实现后端**：对象上传下载、日志追加/对账、索引重建、分页去重与限流。
5. **接入共同引擎**：双端冲突、删除、崩溃恢复与本地保护。
6. **试运行**：先测试 Vault，再小规模真实数据试运行，观察额度和日志增长。

如果所需资源权限无法获批、当前权益无法覆盖预测用量，或无法完成正式身份方案，暂停该路线的正式发布。项目当前最直接的下一步是补文件传输 P0，而不是继续扩展设置页。

## 5. 方案二：纯 GitHub

### 5.1 可行性与两条实现路径

GitHub 能将正文与同步元数据放在同一仓库版本中。相比方案一，它消除了跨平台正文/记录提交的问题；并发编辑、删除与本地写入保护仍由插件负责。

| 路径 | 实现方式 | 适用情况 |
|---|---|---|
| A：原生 Git | 插件控制本机 Git，执行提交、获取、合并、推送 | 仅桌面端、用户熟悉 Git，希望保留普通工作流 |
| B：GitHub REST Git Database API | 插件直接创建 blob/tree/commit，非强制更新同步分支 | 希望安装时不依赖 Git、控制交互并为移动端留空间 |

**本项目自研插件建议优先验证 B。** 它可以只获取当前设备所需内容，不要求完整 clone 历史，也不需要直接在用户 Vault 上执行 checkout/reset。若目标只是尽快满足个人桌面同步，可先试用现有 Obsidian Git 作为需求与体验基线；它已有自动提交/拉取/推送及冲突界面，但作者明确将移动端支持列为实验性且不稳定。[Obsidian Git 官方仓库](https://github.com/Vinzent03/obsidian-git)

移动端不作为首版承诺。使用 API 只减少了原生 Git 依赖，不能解决手机后台挂起、内存、凭证存储和局域网权限等平台问题。

### 5.2 建议仓库与发布结构

使用专用私有仓库和 `obsidian-sync` 分支；仓库应先初始化，再创建同步分支。不要与插件源码放在同一仓库。

```text
vault/                           # 可直接阅读的当前 Markdown
  技术/笔记.md
sync-meta/
  schema.json                    # 协议版本、vault_id
  files/<file_id>.json            # 文件身份、路径、heads、删除状态
  revisions/<分片>/<rev_id>.json  # 不可变修订记录
  conflicts/<file_id>/...         # 冲突分支正文，保持可达
```

正常正文由当前/历史 commit 的文件 blob 保留；修订元数据保存其 blob SHA 与原始字节哈希。并发双方的正文必须出现在成功发布的 tree 或其他保留引用中，不能依赖孤立 blob 永久可用。大规模运行再加入状态快照、日志分段和迁移协议，避免新设备逐条回放所有 JSON。

API 创建 blob 使用 Base64 携带原始字节，避免客户端主动改变 BOM/换行。[Git blobs API](https://docs.github.com/en/rest/git/blobs)

### 5.3 一次可靠上传如何完成

1. 获取当前分支 head `H` 及其 tree，锁定本轮读取的固定版本。
2. 读取相关文件身份与修订，协调本地待提交操作。
3. 创建修改内容及元数据所需的 blob；用 base tree 构造新的 tree，保留无关文件。
4. 创建以 `H` 为父提交的 commit `C`，同一次 tree 包含正文和元数据。[Git commits API](https://docs.github.com/en/rest/git/commits)
5. 更新分支引用到 `C`，使用 `force=false`。同样基于 `H` 的两个并发提交，先发布者成功后，另一个通常因非快进而失败，需要重新协调。[Git references API](https://docs.github.com/en/rest/git/refs)
6. 失败者读取新 head，保留其他设备已发布的内容，用新 head 重建 tree/commit 后重试；同一笔记冲突时保留两个业务修订。

`force=false` 是非快进保护，不是提供任意字段 CAS 的数据库接口。还应使用专用分支、禁止强推/删除的仓库规则，并测试规则与所选凭证的兼容性。

**Git 提交历史与笔记业务版本图要区分。** B 读取了远端新 commit，不代表 B 的离线笔记已经基于 A 的正文修改；重试时仍须保留 B 真正的父修订，不能把改 Git commit 的父节点当作完成了内容合并。首版冲突可保留双方并人工选择；后续再做基于共同祖先的文本三方合并。

分支更新请求超时后，查询当前 head 与已发布修订 ID，判断是否已经成功。临时 Git 对象创建成功不算同步完成；分支引用发布并经对账才算远端确认。轮询取得新 head 后，后续文件读取固定在对应 commit，避免一轮中混入不同版本。

### 5.4 限流、容量与安全

- 普通用户鉴权 REST 请求通常共享 5,000 次/小时主额度；另外还有二级限流，官方列出一般内容创建请求不超过 80 次/分钟、500 次/小时，并可能有更低端点限制。一个业务提交需要多次请求，所以不能把这些数当作“每小时可同步的文件数”。采用批处理、串行发布、退避与响应头预算。[GitHub REST 限流](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)
- Contents API 的目录枚举有 1,000 项限制；全库扫描使用 Trees API，并处理递归响应的 `truncated` 标记。递归树当前文档上限为 100,000 项或 7 MB，超出时分子树读取。[Contents API](https://docs.github.com/en/rest/repos/contents)、[Trees API](https://docs.github.com/en/rest/git/trees)
- GitHub 普通 Git 文件有大文件限制，并建议仓库保持较小。Markdown 很适合这种模型，但高频提交、长期修订元数据和大量二进制也会膨胀；首版维持当前单个 Markdown 5 MiB 的产品限制，不把 Git LFS 自动视为普通 API 同步的一部分。[GitHub 文件与仓库大小说明](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github)
- 先使用用户各自的 fine-grained PAT，仅授权专用仓库的 Contents 读写，并支持到期、撤销和替换；正式面向多人分发再评估 GitHub App/用户授权。应用私钥或共享应用 Secret 不放在插件里。[分支 API 的令牌权限](https://docs.github.com/en/rest/git/refs)
- 私有仓库控制访问，但不等于端到端加密。若要求 GitHub 无法读取内容，需要额外的客户端加密与密钥恢复设计，同时会失去网页直接阅读 Markdown 的便利。
- 国内不同网络访问 GitHub 的表现需在目标设备实测。不能承诺连接质量；断网或限流时继续本地编辑并保留队列。

### 5.5 实施顺序

1. 创建专用测试私有仓库，验证 token 权限、初始化、blob/tree/commit、非强制更新。
2. 做双客户端同 head 竞态、请求超时丢响应、错误凭证、受保护分支、网络中断探针。
3. 明确协议布局、稳定文件身份、修订与冲突正文的可达性。
4. 实现 API 后端、固定 commit 拉取、批量发布和本地持久化重试。
5. 接共同引擎与冲突界面，测试移动、删除、离线编辑、重启与历史恢复。
6. 测试 1,000/5,000/10,000 文件及持续修订后的冷启动时间、请求数与仓库增长；通过后再定实际规模上限。

这条路线的关键 P0 是“并发发布与超时恢复不会丢分支”，而不仅是成功往仓库上传一个文件。

## 6. 方案三：完全自建局域网同步服务

### 6.1 可行性与边界

在 NAS、小主机或常开电脑部署统一服务，插件通过 HTTPS 请求，不让每台电脑直接操作同一份数据库文件。离线设备继续本地编辑，重新接入内网后协调同步。

主要优势是可以自己定义事务、唯一约束、增量游标、配额与恢复规则；主要代价是必须有人维护常开设备、备份、升级和磁盘故障恢复。服务器停机时可继续编辑，但设备间不能经该服务同步。

### 6.2 推荐首版架构

```text
Windows / macOS Obsidian 插件
             │ HTTPS / 可选 WebSocket
             ▼
局域网同步服务（单实例，Node.js + TypeScript）
  ├─ 身份认证、Vault 授权、协议兼容
  ├─ 提交协调、路径占用校验、幂等
  ├─ SQLite：文件、修订、heads、设备、增量日志
  ├─ objects/<hash>：不可变原始正文
  └─ 一致性备份、恢复、健康检查
```

TypeScript 方便与当前插件共享协议类型；Go 也可行，但首版不必为了服务端额外增加语言。此为技术选型建议，不是对目标主机性能的实测结论。

SQLite 放在服务端本机磁盘，由服务进程独占管理；不要把数据库放在 SMB 共享供多设备直连。官方说明 WAL 依赖同机共享内存，不适用于网络文件系统；读写可以并行，但写入仍需排队。初期单实例足够，未来需要多服务实例再评估 PostgreSQL。[SQLite WAL 文档](https://www.sqlite.org/wal.html)

建议数据表：

| 表 | 作用 |
|---|---|
| vaults / devices / grants | Vault、设备、授权和撤销 |
| files | 稳定 file_id、当前路径、删除/冲突状态 |
| revisions / revision_parents | 不可变修订与版本图 |
| file_heads | 一个文件当前的所有版本头 |
| objects | 内容哈希、大小、存储位置 |
| changes | 事务提交时生成的递增 seq 与变化事件 |
| operations | 幂等键、payload 哈希和可重放的提交结果 |

数据库应约束 `(vault_id, revision_id)` 等唯一性。活跃路径占用要按跨平台规则检查；发生重命名分叉时保留所有修订，停止自动物化冲突文件，不让数据库唯一键错误迫使丢弃某一方。

### 6.3 建议接口与提交流程

```text
GET  /v1/health
GET  /v1/vaults/:vault/state                    # 当前快照、协议/快照代次
GET  /v1/vaults/:vault/changes?after=:seq&limit=...
GET  /v1/vaults/:vault/objects/:hash
PUT  /v1/vaults/:vault/objects/:hash             # 内容寻址、哈希校验
POST /v1/vaults/:vault/commits                   # 幂等业务修订提交
GET  /v1/vaults/:vault/operations/:operationId
WS   /v1/vaults/:vault/events                   # 可选，只提示有新 seq
```

对象与数据库跨存储介质，不能声称一次 SQLite 事务就原子写完两者。建议顺序：

1. 接收对象到临时文件，限制大小并计算哈希。
2. 校验通过后持久化文件并原子移入对象区；按目标系统验证 fsync 与断电行为。
3. 开启数据库写事务，检查授权、幂等键、父修订、对象存在与路径约束。
4. 插入修订，计算 heads，写增量事件和操作结果，一起提交。
5. 返回成功；之后才发送 WebSocket 通知。

事务前崩溃最多留下未引用对象，后续可对账；不能提交引用尚未持久化对象的记录。已知父修订但已落后于当前 head 时，可在同一事务追加为冲突分支，返回已保存及 conflicted 状态；未知父节点/非法操作则拒绝并保留客户端待提交队列。删除与修改并发同样形成冲突，禁止按到达顺序静默取胜。

先做分页拉取，后做 WebSocket。推送断开/丢消息时，客户端凭 seq 补拉；游标过期或服务端从旧备份恢复时，用服务端代次识别并要求重新对账，而不是继续沿用不再有效的旧游标。

### 6.4 部署与维护

- 单实例容器 + 持久化目录，提供配置、健康检查、迁移与回滚说明；按目标 NAS/电脑架构打包验证。
- DHCP 地址保留或内部 DNS；首版手动配置地址即可，自动发现后做。
- 使用设备独立 token，服务端存凭证哈希，支持撤销、Vault 隔离与速率限制；内网也使用 TLS，并验证证书信任与客户端连接。
- 正文对象目录不直接当作可编辑共享 Vault。需要人类可读文件夹时生成镜像，外部改动需通过显式导入进入协议。
- 备份包括数据库一致性快照与其引用的对象。首版不自动清理对象时，可以先生成数据库备份，再复制所引用的不可变对象；如果以后引入 GC，必须与备份协调。SQLite 提供在线备份 API 等方式，不应仅复制运行中的主数据库文件。[SQLite 备份文档](https://www.sqlite.org/backup.html)
- 定期做恢复演练：服务器全新部署后，能够从备份恢复，客户端识别恢复代次并重新核对。同步副本不能替代独立备份。
- 首版默认只有局域网可用。异地互联属于后续网络部署范围，不以开放公网数据库端口解决。

### 6.5 可用的现成基线

Self-hosted LiveSync 已提供自托管同步插件，支持 CouchDB 等后端、冲突处理与端到端加密，可在隔离测试 Vault 中作为体验和可靠性基线。若用户最终只需要“自托管同步能用”，先试用可以减少自研投入；若目标是本项目自己的插件与协议，则仍按上述自建服务推进。[Self-hosted LiveSync 官方项目](https://github.com/vrtmrz/obsidian-livesync)

如果未来选择自行对接 CouchDB，不能只读取默认获胜版本。官方冲突模型需要应用显式处理冲突分支；`_changes` 也不保证提供同一文档的每一个中间状态，因此不能直接当作永久审计历史。[CouchDB 冲突模型](https://docs.couchdb.org/en/stable/replication/conflicts.html)、[CouchDB changes feed](https://docs.couchdb.org/en/stable/api/database/changes.html)

## 7. 工作量与成本估算

假设一名熟悉 TypeScript、Obsidian 与同步系统的开发者；仅 Windows/macOS、Markdown、少量设备；包含可恢复队列、冲突、删除保护与基本恢复，不包含移动端、附件、多人权限产品界面及实时协同编辑。

| 工作 | 估算工作日 | 说明 |
|---|---:|---|
| 通用客户端引擎、本地状态、冲突与安全写入验证 | 20–30 | 三种方案都需要；现有原型尚未完成 |
| 飞书专项 P0、后端适配、鉴权组件与容量处理 | 12–22 | 加共同部分约 32–52 工作日 |
| GitHub 专项 P0、API 后端、发布竞争与仓库布局 | 8–16 | 加共同部分约 28–46 工作日 |
| 局域网专项 P0、服务端、部署、备份与恢复 | 12–22 | 加共同部分约 32–52 工作日 |

以上是架构级估算，P0 之后才适合排正式里程碑。外部审批、等待设备和至少约两周的试运行观察时间另计。若字节语义与本地竞争保护出现底层限制，需先调整方案再重新估算；不能为追赶日期省略保护。

| 成本 | 飞书 | GitHub | 自建局域网 |
|---|---|---|---|
| 直接资源成本 | 云盘、表格行数、API 权益；取决于租户套餐 | 仓库/账户权益及必要的额外服务；不承诺无限免费存储 | 常开设备、硬盘、电力、备份介质 |
| 服务组件 | 正式鉴权/API 网关可能需要部署 | PAT 小规模版本可不部署常驻后端；应用授权另评估 | 完整同步服务与维护 |
| 隐性投入 | 管理员配合、权限与套餐变化、日志归档 | 网络可达性、凭证轮换、历史膨胀 | 运维、硬件故障、升级、恢复演练 |

本报告不报价套餐。实际决策应填写目标租户权益、设备数、文件数、每天修订数与附件计划后再算年度成本。

## 8. 建议实施里程碑与验收

1. **P0，约 2–4 工作日/所选路线**：只用测试资源验证最不确定的 API、权限、并发发布和断电/超时语义；并行的概念不代表需要同时开发多个后端。
2. **P1，单端闭环**：扫描、稳定身份、首次绑定、原始字节上传下载、本地队列与重启恢复。
3. **P2，双端可靠性**：不同文件并发、同文件分叉、移动/删除冲突、请求丢响应、本地下载时继续编辑。
4. **P3，运行与恢复**：目标规模性能、额度/磁盘监控、历史恢复、凭证撤销与重新授权、故障提示。
5. **小规模试运行**：先基于真实使用强度记录请求量、修订增长和恢复耗时，再确定正式默认值。

P0 包含在上节后端专项估算内，不重复累加。现有 SPEC 的 T01–T24 可以改为后端无关测试，再增加各路线专项测试。

| 必测场景 | 验收标准 |
|---|---|
| 中文、YAML、双链、CRLF、BOM、空文件 | 原始字节往返哈希符合约定 |
| 双端修改不同文件 | 双方修改都可取得，无回声循环 |
| 双端离线修改同一文件 | 两个分支均持久化且可恢复，显示冲突 |
| 删除与离线修改竞争 | 保留修改并显示删除冲突 |
| 正文成功后提交记录失败 | 不发布悬空版本；可重启续传与对账 |
| 提交成功但响应丢失 | 重试不产生重复逻辑修订 |
| 下载期间本地编辑 | 停止危险覆盖，保留新编辑与远端版本 |
| 403、429、磁盘满、服务不可用 | 不解释成空库/删除，不丢待提交队列 |
| 分页、树截断、游标过期 | 补齐数据或显式重新对账，不漏文件 |
| 重命名/大小写/路径冲突 | 稳定身份正确，越界路径拒绝 |
| 批量删除、长离线设备返回 | 触发删除保护，避免旧数据复活 |
| 从备份或历史恢复到测试环境 | 恢复完整并可重新与客户端协调 |

目前最适合的下一步：按使用环境在“纯 GitHub”与“局域网自建”之间选主路线；飞书作为有明确组织集成需求时的路线。无论选择哪一种，都先实现一个可靠的端到端闭环，再扩展附件、移动端或其他后端。
