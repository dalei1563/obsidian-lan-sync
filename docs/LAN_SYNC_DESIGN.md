# LAN Note Sync v0.2：自建服务与 Obsidian 插件设计

> 归档：本文件记录 v0.2 SQLite 方案。当前设计以 [v0.3 CouchDB 设计](COUCHDB_DESIGN.md) 和 [部署指南](SERVER_QUICKSTART.md) 为准。

日期：2026-11-01。当前开发基线为本设计，取代旧飞书 SPEC 对后端的限定；旧资料保留供参考。

## 产品范围与当前状态

交付一个可本机运行的单实例同步服务，以及可安装的桌面端 Obsidian 插件。无需飞书、GitHub、云账号或预先准备服务器。开发期只使用回环地址与独立测试 Vault；部署期再配置常开主机、TLS 和客户端地址。

首版支持 Markdown 新建、修改、移动、删除、首次绑定预览、离线重试、冲突选择、历史恢复、批量删除保护、设备配对与撤销。文件正文以原始 UTF-8 字节保存，含 BOM、CRLF 和零字节内容。

运行边界：Windows/macOS 桌面 API；当前真机仅验证 Windows。Obsidian 至少 1.11.4，服务端使用已测试的 Node.js 24.15.0（内置 SQLite 3.51.3）。单文件 5 MiB、单 Vault 最多 10,000 个逻辑文件，本地 Markdown 正文合计不超过 128 MiB；这些是首版保护上限，不代表已完成满规模压测。

不包含移动端、附件、隐藏文件、`.obsidian/` 配置、端到端加密、自动文本合并、对象自动清理和实时协同编辑。同步为编辑后约 2 秒防抖、约 5 秒轮询，失败后 5–60 秒退避；暂不使用 WebSocket。正常队列完成后可立即按命令同步。

## 架构

```text
Obsidian 桌面插件
  ├─ 设置：服务地址 → 配对 → 首次预览 → 开始同步
  ├─ Vault 监听 / 定期扫描 / 本地条件写入
  ├─ 协调引擎：基线、离线队列、冲突、删除保护
  ├─ local-state/state.json：原子持久化与应用日志
  ├─ local-state/snapshots：覆盖前原始字节备份
  └─ Obsidian SecretStorage：设备 token
                 │ HTTPS（回环开发允许 HTTP）
                 ▼
Node.js 单实例服务
  ├─ 内置 HTTP(S)，请求大小/频率限制，设备鉴权
  ├─ SQLite：版本 DAG、heads、增量日志、幂等结果
  └─ objects/<vault_id>/<hash-prefix>/<sha256>：不可变正文
```

代码入口：`server/cli.ts`、`server/http.ts`、`server/store.ts`；共享协议在 `shared/protocol.ts`；客户端协调在 `src/sync/engine.ts`，真实 Obsidian 文件适配在 `src/sync/obsidian-vault.ts`。

## 身份与数据模型

远端 Vault 拥有稳定 `vaultId`。每次配对生成独立 `deviceId` 与 256 位随机 token，token 只返回一次，服务端只存 SHA-256。一次性配对码使用 96 位随机数，10 分钟过期并在成功配对事务中消耗；管理员在服务主机通过 CLI 生成与撤销。

设备只可访问自己绑定的远端 Vault。`deviceId` 是修订中的 `clientId`，服务端不允许冒用其他设备提交。设备隔离不等于多租户企业权限系统；服务主机管理员可以读取所有存储内容。

修订格式：

```ts
interface Revision {
  id: string;
  fileId: string;
  parents: string[];
  path: string;
  deleted: boolean;
  hash: string | null;
  size: number;
  clientId: string;
}
```

`fileId` 保持逻辑身份，重命名只改路径。`id` 是修订幂等键。`parents` 指向该文件已知父修订；首次新增为空，解决冲突时引用所有已知 heads。`hash` 是原始正文 SHA-256。删除用 `deleted=true`、`hash=null`、`size=0` 表示；空正文使用空字节的 SHA-256，与删除明确区分。

主要数据库表：

| 表 | 用途 |
|---|---|
| meta | schema、稳定 serverId、当前服务启动 epoch |
| vaults / devices / pairing | 远端库、设备授权、一次性配对 |
| objects | Vault 可访问的正文哈希和大小 |
| revisions | `(vault_id,id)` 唯一的不可变修订与父节点 |
| heads | 每个文件当前未被后续版本包含的版本头 |
| changes | 自增 seq、完整 FileState 事件，支持增量分页 |
| operations | 修订提交时持久化的幂等回执 |

同一 Vault 内不同逻辑文件的活跃路径不得重叠，包含大小写冲突及“文件成为另一个文件的父目录”。路径必须为 NFC、相对 `.md` 路径，拒绝隐藏目录、`..`、反斜杠、控制字符和 Windows 保留名称。本地拒绝经过符号链接的笔记路径。原始正文保留；路径本身的限制会显式报告，不自动改名。

## 可靠提交与冲突

1. 客户端先把完整修订与正文 Base64 快照写入持久化队列，之后才发网络请求。
2. PUT 上传内容寻址对象；服务端验证大小、UTF-8 与 SHA-256。
3. 正文先写临时文件并 fsync，再移入对象区；POSIX 同步目录。Windows 的目录持久性仍需实际掉电验证。
4. POST 提交修订。SQLite 事务中检查父节点、对象、路径、设备与幂等键，再更新 heads、增量事件及幂等结果。
5. 回执确认后更新本地基线。请求超时不删除队列，重发相同修订获得相同逻辑结果。

文件系统与 SQLite 并非跨介质原子事务。对象先于修订持久化，失败时可以留下孤立对象，不允许先公布悬空修订。首版不进行自动 GC。

并发修订示例：

```text
R0 → RA
  ↘ RB
```

RA、RB 同时基于 R0 时两者均保留，返回两个 heads。服务器串行处理请求不会把后到的版本判为赢家。用户可选本地内容或某个远端版本，生成以当前 heads 为父节点的新修订。覆盖前本地内容另存快照；所有已提交历史仍可查看。

解决冲突本身也进入持久化队列，使用 `applyAfter` 标记区分“向远端提交选择”与“在本地应用选择”，避免回执丢失后误把未替换的本地内容当作新编辑重新上传。

新建文件的同名冲突不自动换身份或覆盖：首次绑定会停留在冲突项；两台设备同时创建新文件时，路径占用会拒绝第二个提交并保留本地队列。用户可改名后使用“重试改名后的新文件”继续。

## 拉取、游标与旧备份恢复

初次拉取 `/state` 在 SQLite 读取事务中取得完整 heads 和对应游标；以后每页最多 100 个增量事件。客户端将完整事件保存到本地 remote 缓存后才推进游标，再逐文件应用；未应用内容仍有可恢复的远端记录。

每次启动服务生成新 epoch。服务重启或备份恢复时，客户端重新取快照，并通过 `/check` 批量核对本地已确认的基线修订是否仍存在。缺失版本会阻止该文件自动覆盖，要求显式选择或恢复完整备份；单纯恢复旧数据库不能被解释为“把所有客户端退回旧内容”。

`serverId` 不同则完全停止，避免地址误指向其他服务。日志未裁剪，因此目前没有游标保留期限；未来加入日志压缩时需要新的快照代次协议。

## 本地应用与恢复边界

- 原始读取使用 `Vault.readBinary()`，上传不经过 Markdown 解析或格式化。
- 相同路径已有文件的更新使用 `Vault.process()`；同步回调中比较当前文本重编码后的字节哈希，匹配基线才替换。若文本 API 的 BOM/换行行为不匹配，停止覆盖并提示处理。
- 任何 markdown 编辑器 leaf 中打开的目标文件都暂缓远端替换/删除。用户关闭后可重试；上传自己的本地更改不受影响。
- 写入后再次读取原始字节并校验哈希。异常时保留双方快照并报告，不声称完成同步。
- 删除使用 Obsidian `trashFile`，避免永久删除。批量删除在发送端和接收端都受保护：单批至少 10 篇且占比至少 10%，或至少 5 篇且占比至少 20%，需确认当前精确批次。
- 远端移动采用新路径创建与原路径回收；原文件变化或目标被占用时保留双方并停止。此操作不是跨文件原子事务，可能暂时留下两个路径。
- `state.applying` 先记录将应用的远端版本，重启后检查磁盘实际状态，已落盘的版本只补基线，不反向上传回声。
- 状态文件临时写入、fsync、rename；独占锁避免两个插件实例或重载期间交叉写状态。损坏时停止，不删除状态重新猜测。

Obsidian 的文本条件写入不能扩展成任意外部进程竞争下的跨文件事务。回收和移动仍存在检查到执行之间的竞争窗口，回收站及原始快照用于恢复；不承诺对恶意外部写入者的强原子性。仅改变大小写的跨平台移动、关闭插件期间“同时改名又改内容”等场景仍需人工核对。首版不将这些场景标为已完整验收。

## HTTP API

除 health 与 pair 外都要求 `Authorization: Bearer <device-token>`。

| 方法与路径 | 行为 |
|---|---|
| GET /v1/health | 存活与协议版本，无敏感信息 |
| POST /v1/pair | 一次性码换取独立设备凭证 |
| GET /v1/vaults/:id/state | 一致性全量快照与游标 |
| GET /v1/vaults/:id/changes?after=N&epoch=E | 增量分页与 epoch 校验 |
| POST /v1/vaults/:id/check | 批量核对最多 100 个基线修订是否存在 |
| PUT /v1/vaults/:id/objects/:hash | 上传并校验正文，支持零字节 |
| GET /v1/vaults/:id/objects/:hash | 校验后下载；禁止跨 Vault 读同哈希对象 |
| POST /v1/vaults/:id/commits | 验证并提交不可变修订、幂等结果 |
| GET /v1/vaults/:id/history/:fileId?before=N | 最新 100 条或继续向前分页 |

JSON 请求上限 32 KiB，正文上限 5 MiB。按来源地址限制配对与 API 请求，拒绝时返回 Retry-After；响应不包含 token、SQL 或内部磁盘路径。首版限流是单进程内存限流，不是公网多租户防护设施。

## 部署与后续阶段

服务端 SQLite 和正文都放在主机本地磁盘。Node 内置数据库的实际 SQLite 版本已核验为 3.51.3；不要随意降级到含已知 WAL 缺陷的旧版本。[SQLite WAL 说明](https://www.sqlite.org/wal.html)

CLI 可在线生成一致性数据库备份，再复制不可变对象，最后生成完成标记。恢复时停止服务，将完成的备份复制到新的数据目录，保留原目录，再启动新实例验证。客户端会因 epoch 变化核对历史。不要只复制运行中的 SQLite 主文件或直接编辑数据库。

正式 LAN 使用 TLS；回环地址可 HTTP，非回环明文需要明确选择开发模式。Docker Compose 默认只映射主机回环端口；添加反向代理 TLS 或直接配置服务证书后再开放局域网。Docker/NAS/Linux 和 macOS 尚未实机验证。

下一阶段依次完成：两台真实设备跨网络试运行、macOS 字节与竞争测试、TLS/NAS 部署验收、目标规模性能与长稳测试，然后再考虑实时推送、附件、移动端与安全的历史归档。
